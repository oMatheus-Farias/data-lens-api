# Per-file OCR results for scanned shipment batches

## Context

Issue #2 is the first implementation increment under issue #1. It establishes safe, synchronous PDF intake and local OCR. Document classification and structured field extraction remain for a later increment.

## Goal

Allow an API client to submit one shipment containing multiple scanned PDFs and receive one ordered OCR result per file, with each result tied to its original filename. A failure processing one file must not discard results for the others.

## HTTP contract

- `POST /shipments/extract`
- Request content type: `multipart/form-data`
- The request contains one or more repeated `files` parts.
- Accept at most 10 PDF files, with a maximum size of 25 MiB per file.
- Missing files, malformed multipart data, excess file count, and non-PDF input return HTTP 400 with a clear validation response.
- A PDF that exceeds the per-file size limit returns a `failed` result for that file when the multipart stream can be consumed safely; other files continue processing.
- Results preserve upload order and include the original filename.

Each file result has a `status` and its original `fileName`:

- `unrecognized`: OCR completed, but classification is not implemented in this increment. Include the complete `ocrText`.
- `failed`: processing failed. Include a safe, client-facing `reason`; do not include temporary paths or subprocess output.

The response contains a `documents` array. It does not include structured `fields`, document classification, parser warnings, or an aggregate batch status in this increment. Those belong to the broader issue #1 scope.

## Processing flow

1. Register the official `@fastify/multipart` plugin and validate multipart input, file count, file size, and PDF content.
2. Create a request-scoped temporary directory and write each accepted upload to an application-generated path. Never use the supplied filename as a filesystem path.
3. Process files sequentially with local OCRmyPDF and Tesseract, using Portuguese and English (`por+eng`), deskewing, and OCR sidecar text output.
4. Return one result per accepted file in upload order. Continue to the next file when OCR fails for one file.
5. Remove uploaded PDFs, OCR output PDFs, sidecar text, and the request-scoped directory in a `finally` path.

The API does not send documents to an external service and does not persist uploads or results. The original filename is returned only as a response identifier and is not logged.

## Errors and security

- Request-level validation errors use HTTP 400 and identify the invalid request condition without echoing file contents.
- Per-file OCR errors use `failed` with a stable, safe reason. Raw stderr/stdout, exception messages from subprocesses, and temporary paths are not returned.
- File paths are generated by the application. The uploaded filename is never used to construct a path.
- Per-file failures do not stop processing other valid files.
- No sample document values or personal data are included in source, fixtures, or logs.

## Validation

- HTTP-boundary tests use Fastify injection and a replaceable OCR processor, so they do not require OCR binaries.
- Cover a successful multi-file request, upload-order preservation, an unrecognized OCR result retaining its text, an isolated per-file failure, missing files, malformed multipart input, non-PDF input, the 10-file limit, and the 25 MiB per-file limit.
- Test cleanup of request-scoped temporary files after both success and failure using a test-owned temporary root.
- Validate the supplied PDFs separately as an end-to-end check when OCRmyPDF, Tesseract, and the `por` and `eng` language data are installed. Do not log or commit personal values from those PDFs.

## Out of scope

- Recognizing shipping manifest or DANFE layouts.
- Extracting structured fields, tables, or parser warnings.
- Persisting documents or results, queues, asynchronous processing, cloud OCR, and cross-document reconciliation.
